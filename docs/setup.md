# Setup

Covers: requirements, `.env`, first-time claude login, GitHub token for PR ingestion, podman, deploy keys and auto-push, webapp deployment, stopping/lifecycle, backups, debugging.

Does not cover: adding a project (see [adding-a-project.md](adding-a-project.md)) or the workspace repo contract (see [workspace.md](workspace.md)).

## Requirements

- Docker or Podman
- go-task (`task`)
- git

## .env reference

`task setup` copies `.env.example` to `.env`, generates `SECRET_KEY_BASE`, and fills in `UID`/`GID` from your host user.
Review `.env` after that, then `task build`.

Variables (see `.env.example` for the authoritative list):

- `QUEUE_DOCKERFILE` - build the queue image from `workspace/Dockerfile` instead of the bare base image, to add project build deps.
  Commented out by default; the workspace Dockerfile must start `FROM autoreviewer-base:local`.
- `UID` / `GID` - host uid/gid baked into the queue image so bind-mounted files stay host-owned.
  Set by `task setup`; only needed by hand if you bypass `task` and your host uid isn't 1000.
- `GH_TOKEN` - GitHub token for the `gh` CLI, used to fetch PR metadata when ingesting `pr<n>` topics.
  A PAT with read access to the target repos.
  Commented out by default; git push/pull auth is separate (`task ssh-setup`).
- `AUTO_PUSH` - `1` to push workspace commits after each review.
  Needs `task ssh-setup` first.
  Default `0`.
- `DEFAULT_PROJECT` - project used when you enqueue a bare topic id with no project name.
- `AUTH_MODE` - `none` for no login (default; meant for localhost only - compose binds the webapp port to 127.0.0.1 by default).
  Unset it for Google OIDC.
- `WEBAPP_PORT` - host port the webapp binds to.
  Default 8080.
- `SECRET_KEY_BASE` - Rails secret, required in production mode.
  Generated by `task setup`; generate by hand with `openssl rand -hex 64`.
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` - only needed when `AUTH_MODE` is unset (Google OIDC).
  Also fill `webapp/config/access.yaml`.
- `REINDEX_INTERVAL` - seconds between background reindex checks.
  Default 60.
- `PROXY_NETWORK` - network name used by `compose.proxy.yaml`.
  Default `caddy`.

## First-time claude login

```
task login
```

Runs `claude /login` inside the container, interactively.
Auth is stored in the `home` docker volume (`/home/reviewer`), so it survives image rebuilds and `task down` / `task up` cycles.

Changing `UID` in `.env` after your first `task build` means the container user's home directory changes ownership expectations; if login stops working after a uid change, remove the `home` volume and log in again.

### First-run prompts

The image seeds `~/.claude/settings.json` (theme, and `skipDangerousModePermissionPrompt`) so a fresh `home` volume skips claude's interactive first-run screens - the theme picker and the "bypass permissions, accept the risks" prompt. Without this the first unattended review would hang on the accept screen, since reviews launch with `--dangerously-skip-permissions`.

The seed only lands when the `home` volume is created empty (that's when the volume copies image content). If you already have a `home` volume from an earlier build, it won't pick up the file - remove the volume and re-run `task login`, or write the file by hand: `task shell` then `printf '{"theme":"dark","skipDangerousModePermissionPrompt":true}' > ~/.claude/settings.json`.

The workspace trust dialog ("do you trust the files in this folder?") does not appear for reviews (bypass-permissions mode skips it). It can still show once on interactive `task claude` / `task shell` in a directory you haven't opened before; accept it once and it persists in the `home` volume.

## GitHub token for PR ingestion

Ingesting a `pr<n>` topic reads the PR's metadata through the `gh` CLI, which needs a token.
Set `GH_TOKEN` in `.env` to a GitHub PAT with read access to the target repos and restart (`task down && task up`).
The queue passes it into the container via `env_file`, so no interactive login is needed.

This is separate from the deploy key below: `GH_TOKEN` authenticates the PR metadata API, the deploy key authenticates git push/pull.

## Podman

```
task build DOCKER=podman COMPOSE="podman compose"
```

Pass the same overrides to every other `task` command that touches compose (`up`, `down`, `logs`, etc.) - or export `DOCKER`/`COMPOSE` in your shell.

Rootless podman note: the `.:/app` bind mount needs the container's uid to map to your host uid, or files created in the container (state/, findings via the workspace mount) end up owned by a uid your host user can't manage.
Use `--userns=keep-id`, via a podman-specific compose override.
Example `compose.podman.yaml`:

```yaml
services:
  review-queue:
    userns_mode: "keep-id"
```

This is podman-only - do not add it to the base `compose.yaml`, and don't apply it under docker.
Include it with `-f`:

```
podman compose -f compose.yaml -f compose.podman.yaml --profile queue --profile web up -d
```

## Deploy key and auto-push

```
task ssh-setup
```

Generates an ed25519 key in the container's home volume and prints the public key.
Register it as a **push-capable** deploy key on your workspace repo's forge (GitHub: repo Settings -> Deploy keys, "Allow write access").

Then set `AUTO_PUSH=1` in `.env` and restart (`task down && task up`).
`review-push` runs after each review's completion signal and pushes the workspace's commits.
On push failure the commits stay local and a tmux window named `FAIL-push-<label>` opens with the git error - `task attach` to see it.

## Webapp deployment

### Localhost (default)

`AUTH_MODE=none` in `.env`, `task up` starts both queue and webapp, `http://localhost:8080`.
No Google client id/secret or `access.yaml` needed.
The port is bound to `127.0.0.1` only.

### Server, behind a reverse proxy

```
task up-web
```

starts just the webapp (`--profile web`).
To attach it to an external reverse-proxy network instead of publishing the port, use `compose.proxy.yaml`, exactly as its own header comment says:

```
docker compose -f compose.yaml -f compose.proxy.yaml --profile web up -d
```

The proxy then targets `<compose-project>-webapp-1:80`.

### Google OIDC checklist

1. Unset `AUTH_MODE` in `.env` (or delete the line).
2. Create a Google OAuth client, put `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in `.env`.
3. `cp webapp/config/access.yaml.example webapp/config/access.yaml` and fill in `allowed_domains` / `allowed_emails`.
4. Rebuild: `access.yaml` is baked into the webapp image at build time, so a restart alone does not pick up changes - run `task build` (or rebuild the webapp service) and restart after editing it.

### Static files

Anything under `workspace/public/` is served at `/public/`, behind the same login as the findings.
A directory shows a listing, or its `index.html` if it has one (`?list=1` shows the listing anyway).
Files are sent as-is with the MIME type guessed from the extension, so html/css/js/images render in the browser and everything else downloads.
Names may use letters, digits, `_`, `-` and `.`, but not start with a dot, so dotfiles are hidden; symlinks must stay inside `public/`.

HTML in there runs on the same origin as the review app, so its scripts can act with your session:
only put html there that you wrote or read.

## Stopping and lifecycle

`task down` is **not graceful** to in-flight reviews: it kills the tmux server, which kills any running claude session mid-review.
This is accepted - reviews are resumable, and re-enqueueing the same topic picks up review progress from committed findings.
There is no drain/wait step.

Preflight failures (missing workspace, claude not logged in, etc.) park the `review-queue` container on `sleep infinity` instead of crash-looping, with the failing checks printed.
`task logs` shows the message; fix the issue and `task up` again (or restart just that container).

## Backups

Two named volumes matter: `home` (claude auth, deploy key) and `dbdata` (webapp's sqlite index - safe to delete any time, it's rebuilt from the workspace by reindexing).

The actual review data lives in the workspace, which is a git repo - push it to its own remote.
That's your backup; the volumes are convenience state, not sources of truth.

## Debugging

- `task attach` - attach to the `reviews` tmux session (Ctrl-b d to detach).
- `task shell PROJ=<name>` - shell in the container, in `workspace/<name>` (omit `PROJ` for `workspace/` itself).
- `task logs` - tail queue + webapp container logs.
- `task doctor` - run the same preflight checks the queue runs at startup (`.env` present, `workspace/` present, `bin/review-queue --check`).
- `task proj -- <project> <task> [VARS...]` - run a project-local Taskfile task inside the container, e.g. the postgres cluster helpers: `task proj -- postgres start SRC=t139733`.
