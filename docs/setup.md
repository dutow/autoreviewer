# Setup

Covers: requirements, `.env`, first-time claude login, GitHub token for PR ingestion, podman, deploy keys and auto-push, webapp deployment, the review runner, stopping/lifecycle, backups, debugging.

Does not cover: adding a project (see [adding-a-project.md](adding-a-project.md)) or the workspace repo contract (see [workspace.md](workspace.md)).

## Requirements

- Docker or Podman
- go-task (`task`)
- git

## .env reference

`task setup` copies `.env.example` to `.env`, generates `SECRET_KEY_BASE`, and fills in `UID`/`GID` from your host user.
Review `.env` after that, then `task build`.

Variables (see `.env.example` for the authoritative list):

- `QUEUE_DOCKERFILE` - build the queue image from `workspace/Dockerfile` instead of the bare base image, to add project build deps.
  Commented out by default; the workspace Dockerfile must start `FROM autoreviewer-base:local`.
- `UID` / `GID` - host uid/gid baked into the queue image so bind-mounted files stay host-owned.
  Set by `task setup`; only needed by hand if you bypass `task` and your host uid isn't 1000.
- `GH_TOKEN` - GitHub token for the `gh` CLI, used to fetch PR metadata when ingesting `pr<n>` topics.
  A PAT with read access to the target repos.
  Commented out by default; git push/pull auth is separate (`task ssh-setup`).
- `AUTO_PUSH` - `1` to push workspace commits after each review.
  Needs `task ssh-setup` first.
  Default `0`.
- `DEFAULT_PROJECT` - project used when you enqueue a bare topic id with no project name.
- `AUTH_MODE` - `none` for no login (default; meant for localhost only - compose binds the webapp port to 127.0.0.1 by default).
  Unset it for Google OIDC.
- `WEBAPP_PORT` - host port the webapp binds to.
  Default 8080.
- `SECRET_KEY_BASE` - Rails secret, required in production mode.
  Generated by `task setup`; generate by hand with `openssl rand -hex 64`.
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` - only needed when `AUTH_MODE` is unset (Google OIDC).
  Also fill `webapp/config/access.yaml`.
- `REINDEX_INTERVAL` - seconds between background reindex checks.
  Default 60.
- `PROXY_NETWORK` - network name used by `compose.proxy.yaml`.
  Default `caddy`.

## First-time claude login

```
task login
```

Runs `claude /login` inside the container, interactively.
Auth is stored in the `home` docker volume (`/home/reviewer`), so it survives image rebuilds and `task down` / `task up` cycles.

Changing `UID` in `.env` after your first `task build` means the container user's home directory changes ownership expectations; if login stops working after a uid change, remove the `home` volume and log in again.

### First-run prompts

The image seeds `~/.claude/settings.json` (theme, and `skipDangerousModePermissionPrompt`) so a fresh `home` volume skips claude's interactive first-run screens - the theme picker and the "bypass permissions, accept the risks" prompt. Without this the first unattended review would hang on the accept screen, since reviews launch with `--dangerously-skip-permissions`.

The seed only lands when the `home` volume is created empty (that's when the volume copies image content). If you already have a `home` volume from an earlier build, it won't pick up the file - remove the volume and re-run `task login`, or write the file by hand: `task shell` then `printf '{"theme":"dark","skipDangerousModePermissionPrompt":true}' > ~/.claude/settings.json`.

The workspace trust dialog ("do you trust the files in this folder?") does not appear for reviews (bypass-permissions mode skips it). It can still show once on interactive `task claude` / `task shell` in a directory you haven't opened before; accept it once and it persists in the `home` volume.

### API key warning

`ANTHROPIC_API_KEY` must not be set in the queue's environment.
With the key set, `claude -p` bills the API key instead of your subscription.
The runner prints `WARNING: ANTHROPIC_API_KEY is set; claude -p will bill the API key` at the start of a run, and keeps going.

## GitHub token for PR ingestion

Ingesting a `pr<n>` topic reads the PR's metadata through the `gh` CLI, which needs a token.
Set `GH_TOKEN` in `.env` to a GitHub PAT with read access to the target repos and restart (`task down && task up`).
The queue passes it into the container via `env_file`, so no interactive login is needed.

This is separate from the deploy key below: `GH_TOKEN` authenticates the PR metadata API, the deploy key authenticates git push/pull.

## Podman

```
task build DOCKER=podman COMPOSE="podman compose"
```

Pass the same overrides to every other `task` command that touches compose (`up`, `down`, `logs`, etc.) - or export `DOCKER`/`COMPOSE` in your shell.

Rootless podman note: the `.:/app` bind mount needs the container's uid to map to your host uid, or files created in the container (state/, findings via the workspace mount) end up owned by a uid your host user can't manage.
Use `--userns=keep-id`, via a podman-specific compose override.
Example `compose.podman.yaml`:

```yaml
services:
  review-queue:
    userns_mode: "keep-id"
```

This is podman-only - do not add it to the base `compose.yaml`, and don't apply it under docker.
Include it with `-f`:

```
podman compose -f compose.yaml -f compose.podman.yaml --profile queue --profile web up -d
```

## Deploy key and auto-push

```
task ssh-setup
```

Generates an ed25519 key in the container's home volume and prints the public key.
Register it as a **push-capable** deploy key on your workspace repo's forge (GitHub: repo Settings -> Deploy keys, "Allow write access").

Then set `AUTO_PUSH=1` in `.env` and restart (`task down && task up`).
`review-push` runs after each review's completion signal and pushes the workspace's commits.
On push failure the commits stay local and a tmux window named `FAIL-push-<label>` opens with the git error - `task attach` to see it.

## Webapp deployment

### Localhost (default)

`AUTH_MODE=none` in `.env`, `task up` starts both queue and webapp, `http://localhost:8080`.
No Google client id/secret or `access.yaml` needed.
The port is bound to `127.0.0.1` only.

### Server, behind a reverse proxy

```
task up-web
```

starts just the webapp (`--profile web`).
To attach it to an external reverse-proxy network instead of publishing the port, use `compose.proxy.yaml`, exactly as its own header comment says:

```
docker compose -f compose.yaml -f compose.proxy.yaml --profile web up -d
```

The proxy then targets `<compose-project>-webapp-1:80`.

### Google OIDC checklist

1. Unset `AUTH_MODE` in `.env` (or delete the line).
2. Create a Google OAuth client, put `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in `.env`.
3. `cp webapp/config/access.yaml.example webapp/config/access.yaml` and fill in `allowed_domains` / `allowed_emails`.
4. Rebuild: `access.yaml` is baked into the webapp image at build time, so a restart alone does not pick up changes - run `task build` (or rebuild the webapp service) and restart after editing it.

### Static files

Anything under `workspace/public/` is served at `/public/`, behind the same login as the findings.
A directory shows a listing, or its `index.html` if it has one (`?list=1` shows the listing anyway).
Files are sent as-is with the MIME type guessed from the extension, so html/css/js/images render in the browser and everything else downloads.
Names may use letters, digits, `_`, `-` and `.`, but not start with a dot, so dotfiles are hidden; symlinks must stay inside `public/`.

HTML in there runs on the same origin as the review app, so its scripts can act with your session:
only put html there that you wrote or read.

## Review runner

The queue starts each review as `bin/review-run --done-file <signal> <project> <topic>` in its tmux window.
Commit reviews run as `bin/review-run --done-file <signal> --commits <project> <from>..<to>`.
The runner runs one headless `claude -p` session per phase of the project's route (see [adding-a-project.md](adding-a-project.md#review-phases)), with `--dangerously-skip-permissions` and `AskUserQuestion` disallowed.
It touches the done file when it ends, success or failure, so the window closes the same way as before.
The done file is new for every launch (`state/signals/<window>-<time>-<pid>-<n>.done`), and the auto-close watcher kills the tmux window by the id it got at creation, not by name.
A watcher left over from an older run of the same topic therefore never closes a newer review's window.
Phase sessions do not get `REVIEW_DONE_FILE`, so the workspace Stop hook does nothing in them.
They get `REVIEW_RUN=1` instead, the marker workspace hooks use to tell a review session (`REVIEW_DONE_FILE` or `REVIEW_RUN` set) from an interactive one: the example `PermissionRequest` hook allows only when one of them is set.
They also get `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, so a phase cannot leave background work behind.

`CLAUDE_BIN` sets the claude binary the runner calls (default `claude`).
`WORKSPACE_DIR` and `STATE_DIR` override the workspace and state paths, as for the queue.

Each phase output is committed in the workspace, and `usage.json` is committed after the last phase.
A failed phase stops the review, prints `FAILED: <reason>`, and opens a tmux window `FAIL-<project>-<topic>` with the message.

### Logs and usage

- `state/logs/<project>-<topic>-v<N>/<NN>-<phase>.jsonl` - the raw stream-json output of each phase session, appended on every run.
  Commit reviews log to `state/logs/<project>-commits-<from>-<to>/commits.jsonl`.
  `bin/review-prune` removes log dirs untouched for `REVIEW_PRUNE_DAYS` days (see [Pruning](#pruning-old-builds-and-worktrees)).
- `state/usage.log` - one JSON line per finished or limit-interrupted phase: time, project, topic, version, route, phase, model, status (`ok`, `failed`, `limit`), cost and tokens.
- `<project>/findings/<topic>/vNN/usage.json` - committed with the findings: route, claude version, per-phase tokens, cost and duration, and totals.
  Runs cut short by the usage limit are in it too, with status `limit`, so the totals are the full cost of the review.
  A re-run that runs no phase leaves `usage.json` as it is, and creates none.
  The webapp shows the cost on the review.

### Usage limit pause

When a phase hits the claude usage limit, the runner writes `state/paused` (the reset time plus a two minute margin, and the window that set it), waits, and runs the phase again.
A run counts as a limit hit when the stream had a `rate_limit_event` with status `rejected` and the run did not end cleanly, or when it ended with an error result reading `You've hit your ... limit`.
The reset time is the event's `resetsAt`; without one it is parsed from the message (`resets 3pm`, `resets Nov 24, 3pm`, as local time), and when that fails too the runner waits an hour.
It always waits at least five minutes.
It gives up after 5 retries and fails the review.
While `state/paused` is in the future the queue starts no new review; it prints `paused until ... (usage limit)` once and polls every 30 seconds.
The runner removes the file after a successful retry.
The queue removes it once the time has passed, or when it is corrupt.
To lift a pause by hand, delete `state/paused`.

### Resume

Re-running a review for the same topic and version continues where it stopped.
A phase is skipped when its output file already exists and its last run in `usage.json` did not fail or hit the usage limit; a skipped phase's output is still committed.
A phase whose last run failed or hit the limit is run again, even if it left an output file.
To redo a phase, delete its output file.

### Running by hand

From the workspace directory, inside the container (`task shell`):

```
../bin/review-run <project> <topic>
../bin/review-run --route full <project> <topic>
../bin/review-run --render design <project> <topic>
../bin/review-run --commits <project> <from>..<to>
```

`--route NAME` overrides `review.route`.
`--render PHASE` prints the prompt that phase would get and exits, without calling claude.
`--done-file PATH` touches `PATH` when the run ends; the queue uses it, you normally do not.
The topic must already be ingested (`review/<topic>/metadata.json` exists).
Exit status is 0 on success, 1 on failure.

### Replaying a review

A replay re-runs a past review version through a route without touching the workspace repo.
It is how a route is checked before a project switches to it: replay a few reviewed topics on the new route and compare their postable points with the original reviews.
Replaying some of the same topics on `single` again shows how much two runs differ on their own.

```
task replay -- <project> <topic> <vN> <route>    # tmux window "replay", watch with task attach
task compare -- <run dir> <reference dir>         # one Opus session, a few minutes
task compare -- --table                           # one line per compare
```

Inside the container the same commands are `bin/review-replay [--keep-worktree] <project> <topic> <vN> <route>` and `bin/review-compare`, run from the repo root.
`review-replay` prints the run dir and the `review-compare` command line for it when it ends.

A replay needs the live `review/<topic>` still at vN (`metadata.json` version N), and reuses that ingest and build.
A topic that got a newer version since, or was pruned, cannot be replayed.
`builds/` is shared with the live queue, so avoid topics likely to get a new version while the replay runs; the replay warns when the live review changed under it.

Each run gets `replay/<project>/<topic>/vN-<route>-<n>/`:

- `ws/` - a `git clone --shared` of the workspace with no remote.
  vN and later versions of the topic are dropped from it, `master/`, `branches/` and `builds/` are symlinks to the live ones, and `review/<topic>` is its own worktree at the live review HEAD, removed at the end unless `--keep-worktree`.
  Phase commits land in this clone only.
- `findings` - link to the replayed findings dir in `ws/`.
- `state/` - the runner's state dir (logs, `usage.log`, pause file), separate from the queue's.
- `replay.json` - project, topic, version, route, reference dir, review HEAD, start and end time, `ok`, `inputs_changed`, `cost_usd`.
- `compare-<label>.md` and `.json` - written by `review-compare`; `<label>` is `reference` for the original review, or the other run's dir name when comparing two replays.

The reference `discussion.txt` is copied into the replay findings dir before the run, and `review-run --replay` tells each phase to use it instead of fetching the thread again, so the replay sees the thread as the original review did.

`review-compare` matches the POST and POST-MINOR points of the replay against the reference: matched, only in the reference, only in the replay, with a one-line reason each.
It adds both sides' usage totals to the json.
It refuses a replay without `05-summary.md`, a reference dir other than the one in `replay.json`, and a second run of a different topic or version.
`--table` marks runs that failed (`[replay failed]`) or whose live review changed under them (`[inputs changed]`); leave those out of the gate.
Read the `only_reference` items in the md before trusting the counts.

Replays spend subscription tokens like a review, plus a dollar or two per compare.
`replay/` is gitignored and not indexed by the webapp.
To delete a run, `rm -rf replay/<project>/<topic>/<run>`; if the replay was killed, also run `git -C workspace/<project>/master worktree prune`.

## Pruning old builds and worktrees

Builds and review worktrees pile up: a postgres topic is a few GB, so a few months of reviews fill a disk.
`bin/review-prune` removes `<name>/builds/<topic>/` and `<name>/review/<topic>/` for every topic untouched for `REVIEW_PRUNE_DAYS` days (default 7, `0` disables).
A topic's age is the newest mtime across its build dir, its `status.yaml` files and its review worktree, so a re-review restarts the clock.
It never touches `builds/master`, builds named after a `branches/` checkout (the stable-branch installs other projects build against), a topic whose review tmux window is still open, or a topic a replay is running on (it has a worktree under `replay/`).
Findings are untouched: they live in `findings/` and are committed.
It also removes runner log dirs under `state/logs/` whose newest file is older than the same cutoff; it finds the state dir like the queue does (`STATE_DIR`, default `state/`).

The queue runs it at startup and before each build, so the space is freed before the next build needs it.
Run it by hand, or preview what would go:

```
task prune -- --dry-run
task prune -- --days 30
```

A pruned topic can always be reviewed again: `task enqueue` re-ingests and rebuilds it from scratch, and the findings version keeps counting up from the committed `findings/<topic>/v*` dirs.

## Stopping and lifecycle

`task down` is **not graceful** to in-flight reviews: it kills the tmux server, which kills any running claude session mid-review.
This is accepted - reviews are resumable, and re-enqueueing the same topic skips the phases that already finished (see [Resume](#resume)).
There is no drain/wait step.

Preflight failures (missing workspace, claude not logged in, etc.) park the `review-queue` container on `sleep infinity` instead of crash-looping, with the failing checks printed.
`task logs` shows the message; fix the issue and `task up` again (or restart just that container).

## Backups

Two named volumes matter: `home` (claude auth, deploy key) and `dbdata` (webapp's sqlite index - safe to delete any time, it's rebuilt from the workspace by reindexing).

The actual review data lives in the workspace, which is a git repo - push it to its own remote.
That's your backup; the volumes are convenience state, not sources of truth.

## Debugging

- `task attach` - attach to the `reviews` tmux session (Ctrl-b d to detach).
- `state/logs/<project>-<topic>-v<N>/` - raw per-phase logs of the runner; `state/usage.log` - cost per phase.
- `task shell PROJ=<name>` - shell in the container, in `workspace/<name>` (omit `PROJ` for `workspace/` itself).
- `task logs` - tail queue + webapp container logs.
- `task doctor` - run the same preflight checks the queue runs at startup (`.env` present, `workspace/` present, `bin/review-queue --check`).
- `task proj -- <project> <task> [VARS...]` - run a project-local Taskfile task inside the container, e.g. the postgres cluster helpers: `task proj -- postgres start SRC=t139733`.
